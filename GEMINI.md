# Инструкции и регламент разработки для агентов (GEMINI.md)

Данный документ определяет стандарты качества, правила рабочего процесса и инженерную культуру при разработке мобильного клиентского приложения **Finance App Mobile (getbalanceai_mobile)** на Flutter.

Каждый агент обязан следовать этим инструкциям при выполнении любой задачи.

---

## 1. Базовые принципы и культура кода

* **Production-grade качество**: Это боевое финансовое мобильное приложение для iOS и Android. Код должен быть надежным, безопасным, энергоэффективным, строго типизированным и поддерживаемым.
* **Никакого мусора и отладочных хвостов**:
  * Категорически запрещены комментарии вида `// AI generated`, `// Generated by Gemini`, `// Temporary fix`, `// TODO for AI`, отладочные метки или мусорные заметки.
  * Все комментарии и docstrings должны быть профессиональными, лаконичными и описывать предметную область на русском языке.
  * **Категорический запрет `print()` и `debugPrint()`**: во всех слоях приложения (`lib/`) логирование выполняется **исключительно** через единый логгер `AppLogger` (`Talker`). Прямые вызовы `debugPrint` или `print` считаются критической ошибкой качества кода.
  * Не оставлять закомментированный неиспользуемый код или временные файлы.
* **Надежность типизации и безопасность инициализации**:
  * **Запрет небезопасных `late` синглтонов и менеджеров**: поля глобального доступа (например, `LanguageManager.l10n`) обязаны иметь ленивую инициализацию или безопасный fallback (`lookupAppLocalizations(...)`), исключающий `LateInitializationError` при выполнении изолированных модульных тестов.
  * **Защита от затенения имен (Name Shadowing)**: параметры методов утилит и логгеров не должны дублировать имена методов класса (например, `static void e(dynamic msg, [dynamic error...]) => error(...)` затеняет метод и вызывает `NoSuchMethodError`). Делегирование выполняется напрямую в целевой объект (`talker.error(...)`).
* **Архитектурный источник правды**: Вся разработка опирается на [ARCHITECTURE.md](file:///Users/user/getbalanceai_mobile/ARCHITECTURE.md), [README.md](file:///Users/user/getbalanceai_mobile/README.md) и [REVIEW_CHECKLIST.md](file:///Users/user/getbalanceai_mobile/REVIEW_CHECKLIST.md). Запрещено нарушать границы слоев.

## 2. Жизненный цикл задачи (Workflow)

При получении любой задачи агент строго следует следующему регламенту:

### Шаг 1. Ветвление в Git
* **Всегда ответвляться от актуального `main`**:
  ```bash
  git checkout main
  git pull origin main
  git checkout -b <type>/<task-semantic-name>
  ```
* Использовать семантические префиксы:
  * `feat/` — новый функционал
  * `fix/` — исправление багов
  * `refactor/` — рефакторинг без изменения контрактов
  * `test/` — добавление или правка тестов
  * `docs/` — обновление документации
  * `chore/` — инфраструктурные и сборочные изменения
* **Прямые коммиты в `main` строго запрещены**. Вся работа ведется только через тематические ветки.

### Шаг 2. Разработка с учетом слоев (Layered Architecture)
* Соблюдать строгую изоляцию ответственности:
  * **Screens & Widgets** (`lib/screens/`, `lib/widgets/`): отображение UI (Material 3), получение данных из Cubit, пользовательские жесты. Никакой прямой бизнес-логики.
  * **Cubits & State** (`lib/cubits/`): управление состоянием экрана/фичи, реакция на события, отмена сетевых запросов (`CancelToken`), подписка на сервисы. Без зависимостей от `BuildContext`.
  * **Services** (`lib/services/`): сетевой клиент (`Dio`), локальная база (`ObjectBox`), безопасное хранилище токенов (`FlutterSecureStorage`), интерцепторы трассировки и логирования.
  * **Models** (`lib/models/`): DTO для REST API и сущности локальной базы ObjectBox (`@Entity()`). Безопасный парсинг денежных сумм (`parseAmount()`) и дат (UTC ISO 8601).
  * **Config & Utils** (`lib/config/`, `lib/utils/`): конфигурация окружений (`EnvironmentConfig`), логгер (`AppLogger`), хелперы.
* При работе в конкретных директориях автоматически применяются локальные правила:
  * [lib/screens/GEMINI.md](file:///Users/user/getbalanceai_mobile/lib/screens/GEMINI.md)
  * [lib/cubits/GEMINI.md](file:///Users/user/getbalanceai_mobile/lib/cubits/GEMINI.md)
  * [lib/services/GEMINI.md](file:///Users/user/getbalanceai_mobile/lib/services/GEMINI.md)
  * [lib/models/GEMINI.md](file:///Users/user/getbalanceai_mobile/lib/models/GEMINI.md)
  * [test/GEMINI.md](file:///Users/user/getbalanceai_mobile/test/GEMINI.md)

### Шаг 3. Тестирование
* При добавлении или изменении логики агент **обязан** обновить или расширить модульные тесты и тесты состояний (bloc_test) в `test/`.
* Покрывать как успешные кейсы, так и негативные сценарии (ошибки валидации, 401/403/404, 429 Rate Limit, 503 Service Unavailable, офлайн-режим).
* **Не запускать тесты автоматически при коммите/пуше**: перед коммитом и пушем агент **не должен** сам прогонять тесты. Пользователь прогоняет тесты самостоятельно либо они выполняются хуками (`.githooks/pre-commit`). Если требуется прогон — явно уведомить пользователя и предоставить команду:
  ```bash
  fvm flutter test
  ```

### Шаг 4. Линтеры и форматирование кода
* Код должен строго соответствовать стандартам:
  * **flutter_lints** согласно конфигурации в `analysis_options.yaml`.
  * **dart format** с соблюдением максимальной длины строки и форматирования Dart.
* Не оставлять неиспользуемых импортов, предупреждений компилятора (`dead code`, `unused variable`) или устаревших API.
* **Не запускать линтеры перед пушем/коммитом**: на это настроен git pre-commit хук репозитория и пользователь сам выполняет эти проверки. Агент пишет код чисто сразу, без необходимости вызова проверочных команд перед пушем.

### Шаг 5. Кодогенерация (ObjectBox / Build Runner)
* Если задача затрагивает модели данных ObjectBox (`lib/models/` с аннотацией `@Entity()`):
  1. Обязательно предупредить пользователя о необходимости запуска кодогенератора и предоставить готовую команду:
     ```bash
     fvm flutter pub run build_runner build --delete-conflicting-outputs
     ```
  2. Файлы `lib/objectbox.g.dart` и `lib/objectbox-model.json` обязательны для фиксации в репозитории (хранят стабильные ID схемы БД).

### Шаг 6. Зависимости и окружение
* Если изменены `pubspec.yaml`, `.env`, `.env.example` или `.fvmrc`:
  * Явно уведомить пользователя о необходимости обновления зависимостей:
    ```bash
    fvm flutter pub get
    ```

### Шаг 7. Обязательный этап Код-Ревью (Senior Reviewer)
Перед сдачей результата пользователю проводится критическое код-ревью в роли независимого Senior Reviewer по чек-листу:
1. **Чистота кода**:
   * Полное отсутствие `print()` и `debugPrint()` в `lib/` (проверить поиском по проекту).
   * Отсутствие мусорных комментариев, ИИ-меток, временных костылей и лишних файлов.
   * Отсутствие затенения имен методов класса параметрами функций (Name Shadowing).
2. **Архитектура и декомпозиция**:
   * Соблюдены ли границы слоев, не импортируется ли `main.dart` в экранах и сервисах, изолирован ли Cubit от `BuildContext`.
   * Монолитные сервисы декомпозированы на предметные подсервисы (например, `ApiService` разбит на `AuthApiService`, `TransactionApiService`, `BudgetApiService`, `SyncService`).
   * Логирование централизовано в `AppLogger` (`Talker`), отсутствуют параллельные пакеты логирования.
3. **Безопасность**:
   * Безопасно ли сохраняются JWT-токены (`FlutterSecureStorage`), не логируются ли пароли и секреты в `Talker`, защищены ли эндпоинты от зацикливания 401.
4. **UI/UX и Material 3**:
   * Нет ли хардкода цветов (использовать `Theme.of(context).colorScheme`), локализованы ли строки через `AppLocalizations` (никаких хардкодных мап переводов в коде), обработаны ли состояния загрузки, пустых списков, 429 и 503 ошибок.
5. **Производительность**:
   * Нет ли утечек памяти, закрываются ли `StreamSubscription` и `CancelToken` в `close()`, проверяется ли `mounted` перед `setState()` / `isClosed` перед `emit()`.
6. **Тестируемость и стабильность тестов**:
   * Все поля глобального доступа (`LanguageManager.l10n`) имеют ленивый fallback, исключающий `LateInitializationError`.
   * Тесты с сервисами содержат инициализацию моков платформ (`FlutterSecureStorage.setMockInitialValues({})`, `SharedPreferences.setMockInitialValues({})`).
   * Тесты всплывающих уведомлений (`SnackBar`) используют контролируемый шаг таймера (`tester.pump()` + `tester.pump(const Duration(milliseconds: 500))`) вместо `pumpAndSettle()`.
